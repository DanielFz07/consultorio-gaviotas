PRODUCTO Y DISEÑO
Product
PRODUCT.md

Platform

web

Users

Primary: Administrator (control global). Manages users, master catalogs (services, products), configures global parameters, monitors inventory thresholds, and runs end-of-day reconciliation. Optimizes the interface for this role: dense data, full information surface, keyboard-friendly tables, fast filters, batch actions.

Secondary audiences that must not be blocked by the admin-centric layout:

  • Reception (Recepcionista): operates the front desk, registers owners and pets, schedules/reprograms/cancels appointments, takes payment at checkout. Needs a high-volume, low-friction path for: find owner → register pet → schedule slot → print receipt. Should not be punished for not being the admin; sidebar, color-coding, and shortcuts reflect the same vocabulary.
  • Veterinarian (Veterinario): runs the clinical session. Reads clinical history, opens the consultation, prescribes, attaches lab/imaging files, finalizes the consultation (which emits the invoice). Values legible medical typography and zero-friction access to history, not interface flourishes.
  • Cashier (Caja): role is RECEPCION with payment permission. Reuses the same UI as reception; no separate surface.

Job-to-be-done (admin, primary): "I need to know, in under 10 seconds, whether the clinic is operating normally today: appointments attended, revenue captured, products consumed, and stock that needs replenishment before tomorrow."

Product Purpose

VetSys is an integrated management system for small veterinary clinics (typically 1–3 vets, 1–2 front-desk staff). It replaces the manual notebook + spreadsheet + paper invoice triad that small clinics in Latin America still use. The product exists to:

  1. Eliminate manual calculation errors in invoicing.
  2. Centralize the pet clinical history so it is never lost or duplicated.
  3. Keep stock synchronized with prescriptions in real time (every dispensed dose is a stock decrement).
  4. Reduce no-shows via automated 24-hour reminders.
  5. Produce operational metrics the clinic never had before (daily revenue, top services, low-stock alerts).

Success means a clinic can run a full day with the system, lose zero inventory between prescription and billing, and produce a daily report without any hand-tallying.

Positioning

The mechanism a neighboring product could not truthfully copy: a single transactional boundary that ties a consultation to its prescriptions to its invoice to its stock decrement. When the vet presses "Finalize Consultation", a Postgres BEGIN/COMMIT block guarantees that the invoice number, the items, the stock update, and the history entry are written atomically or not at all. No partial state, no "the stock said yes but the invoice didn't print" race condition. This is the core of the product's reliability story and the reason a clinic can trust it more than a spreadsheet.

Operating Context

  • Environment: physical reception desk, single-screen PC (1920×1080 typical), sometimes a tablet in the consultation room.
  • Workflow cadence: ~8–15 consultations/day, peak in the morning. Each consultation averages 15–20 minutes of clinical time plus 3–5 minutes of system entry.
  • Daily ritual: reception prints the day's appointments at 08:30, vets pull up consultations as patients arrive, cashier closes unpaid invoices at end of day, admin reconciles stock at 19:00.
  • Connectivity assumption: server reachable on the local network; intermittent outages tolerated (queries retry, file uploads resume).
  • Documents handled: lab PDFs, radiograph images (PNG/JPEG/WEBP), printed invoices (PDF export), emailed reminders (SMTP).
  • Regulatory light: no HIPAA-equivalent in the target market, but personal data of pet owners (DNI, email, phone) is treated with restraint. No data leaves the clinic's server without the admin's explicit action.

Capabilities and Constraints

Confirmed capabilities:

  • CRUD for owners (duenos) and pets (mascotas) with 1:N owner→pets and 1:1 pet→clinical-history.
  • Appointment scheduling with slot-uniqueness enforcement per veterinarian.
  • Consultation workflow: symptoms, diagnosis, treatment, services, prescriptions, file attachments, finalize.
  • Inventory: products with stock, minimum-threshold alerts, atomic decrement on prescription.
  • Invoicing: auto-generated on consultation close, sequential correlative numbers, services + products + tax.
  • Authentication with JWT + bcrypt, three roles (Admin / Veterinario / Recepción), RBAC enforced server-side.
  • Worker process polls every 60s for 24h-appointment reminders and sends via SMTP.
  • Backend: Bun + Elysia + TypeScript. Database: PostgreSQL 16. Storage: local volume. Deployment: docker-compose.

Confirmed technical constraints:

  • Backend runs on Linux inside Docker. No Windows-specific paths.
  • Database is strictly relational (PostgreSQL 16). No NoSQL.
  • Files served from ./data/uploads volume; max 10 MB per file; allowed MIME: PNG, JPEG, WEBP, PDF.
  • Frontend is Astro SSR with Node adapter; the SSR layer proxies all auth to the backend.
  • Tax rate is a single configuration value (TAX_RATE env, default 0.16).
  • Sequential invoice numbers via a Postgres SEQUENCE; no manual override.

Explicitly undecided (do not invent):

  • Multi-clinic (chain) tenancy. Current design is single-clinic.
  • Native mobile app. The system is responsive but not native.
  • Payment gateway integration (cards, transfers). Only cash/manual recording exists.
  • SMS provider. Only SMTP email reminders are wired; SMS is a future hook.

Brand Commitments

  • Name: VetSys. Established by the academic project; do not rename or reskin the name.
  • Voice: professional, concise, clinical. No exclamation marks, no emoji in product copy, no marketing language. Empty states say "No hay citas para hoy." not "Uh oh! Nothing here yet!"
  • Identity constraint: the system name "VetSys" and the wordmark in the sidebar must remain on every page that is part of the operator's daily flow.
  • No binding aesthetic pinned yet. Visual world is recorded in DESIGN.md after document runs against the current implementation; polish and later commands will refine it.

Evidence on Hand

  • The implemented system is itself the evidence: every flow described in the manual-of-operations document is live in the running system.
  • The product has no public marketing site, no customer testimonials, no press, no case study. Future work must not fabricate any.
  • The visual reference set is empty; the only incumbent truth is the current Astro implementation in apps/frontend/.

Product Principles

  1. One transaction, one truth. A consultation, its prescriptions, its invoice, its stock decrement, and its history entry are inseparable. Never split them.
  2. The admin sees everything; the role only gates. The primary user is the admin, so density and completeness outrank decoration; role-based hiding prevents unauthorized actions but does not simplify the admin's view.
  3. Reversible on paper, irreversible in the system. A no-show is logged, a cancellation is kept with its reason, an invoice can be annulled (not deleted) — but the system never silently overwrites. Auditability over convenience.
  4. Boring beats clever at the desk. Reception processes dozens of customers a day. The interface must be predictable, keyboard-friendly, and free of animations that delay actions.
  5. Local clinic, real network. No external SaaS dependency, no telemetry, no third-party tracker. The clinic owns the server, owns the data, owns the backup.

Accessibility & Inclusion

  • Target: WCAG 2.1 Level AA.
  • All interactive elements reachable by keyboard; visible focus rings on all focusable elements.
  • Text contrast ≥ 4.5:1 against the surface background; non-text UI contrast ≥ 3:1.
  • Form fields have associated <label> elements; error messages are programmatically associated via aria-describedby or equivalent.
  • Color is never the sole carrier of state (badges pair color with text).
  • Tables are responsive on tablet widths (≥ 768px); below that, the operator is expected to use a dedicated device.
  • Spanish-language UI. No localization infrastructure (i18n) is in scope for v1; copy is written directly in Spanish.
Design
DESIGN.md

World

VetSys is committed to a single visual world: the ficha clínica unificada — the unified clinical card. Every screen is one ruled paper sheet, the way a small Latin American clinic has always organized its patient binder. The system is the binder, digitized.

Three artifacts of the audience's daily life fuse into one form: the pharmacy cardex (the ruled stock card with hand-numbered rows and a single color tab), the historia clínica folder (the manila file with a patient sticker and stamped entries inside), and the factura/recibo (the numbered, ruled, stamped paper with a totals box). The product truth — "one transaction, one truth" — already lives in the database; the visual world makes the same promise felt at the desk.

The category habit this world refuses: the SaaS "stat cards in a card in a card in a sidebar" template. The replacement: one sheet, one ink, one tab strip, sections separated by hairline rules.

Mode

Operate. Density outranks expression. Every affordance is keyboard-reachable. The visitor's success is the admin's success: know in 10 seconds whether the clinic is operating normally today.

Color strategy

Restrained: warm off-white paper, ink black, one clinical-green accent.

Dark/light is not a default; it is a scene. The clinic desk is under fluorescent daylight, paper in hand, screen on. The page is paper, not terminal.

Typography

The audience reads printed medical forms, stamped receipts, and labels. The system uses two faces, both with full Latin Extended for Spanish:

  • IBM Plex Sans — body, headings, UI labels. 300, 400, 500, 600.
  • IBM Plex Mono — numbers, stock counts, money, codes, IDs, times. 400, 500. Tabular numerals always.

Display caps at 6rem. Body measure 60–72ch. Tracking floor −0.02em on large display, normal on body. Number columns use tabular-lining figures (Plex Mono is tabular by default).

Forbidden in the system: Inter, system-default sans, anything that signals "AI-generated dashboard." Plex is not on the training-data default list and was chosen because the audience already sees it on the labels of every pharmacy brand they trust.

Composition

The page is a sheet. Every page has the same four horizontal bands, top to bottom:

  1. Stamp band (40px tall): clinic name stamped left, date and user stamped right, like a paper form's printed header. 1px rule below.
  2. Tab strip (44px tall): horizontal nav of 5 primary destinations. Tabs are separated by 1px rules, not boxes. Active tab has a 2px bottom rule in --accent and ink text. Inactive tabs are muted. The strip is the navigation; there is no sidebar.
  3. Sheet body: 1 card-less ruled paper, max 1200px wide, centered. Sections inside separated by hairline rules. The active page lives in a single column on desktop; on tablet (≥ 768px) some pages split into a 2/3 + 1/3 right rail showing the "active patient file" or relevant context.
  4. Stamp footer (28px tall): system name + page + version. 1px rule above.

No drop shadows. No gradient fills. No border-left > 1px. Cards are forbidden; sections separated by rules only.

Tables

  • Header row: 11px uppercase, tracked 0.04em, --ink-2, on --paper.
  • Body rows: 14px, --ink, 1px --rule-soft between rows, no vertical rules.
  • Number columns: right-aligned, IBM Plex Mono, tabular.
  • Status column: not color alone — uppercase text + a 2px square swatch in the relevant color, so a colorblind operator still reads the state.
  • Row height 40px minimum to support touch and click on tablet.
  • No zebra striping. The hairline rule is the separator.

Controls

  • Buttons: rectangular, 1px --ink border, no border-radius (rounded 2px only). Primary: filled --ink, white text. Secondary: paper background, ink text. Ghost: no border, accent text. Danger: filled --danger. Height 36px. No drop shadow. Hover: invert (paper becomes ink, text becomes paper).
  • Inputs: 1px --ink-2 border, no radius, paper background. Focus: 2px --accent outer outline. Label above input, 12px uppercase tracked.
  • Selects: same. Custom caret drawn with a 1px SVG triangle, not the browser default.
  • Form rows: label column 180px, input column fluid, helper text below in 12px.
  • Modals: only for destructive confirmations and "log out". Never for routine data entry.

States

  • Hover on rows and buttons: invert within 80ms.
  • Focus visible: 2px accent outline, never removed.
  • Loading: button text replaced by "…" plus a 1px progress underline, no spinners.
  • Empty states: a single hairline-bordered "card-less" block, a single sentence ("No hay citas para hoy."), and one contextual action ("+ Nueva cita"). No illustrations.
  • Error: 1px --danger top border on a paper block, monospace code + Spanish message.

Motion

One authored moment, no others. The active tab's 2px bottom rule slides between tabs on route change (200ms, ease-out). That is the only animation in the system. Hover inversions, focus outlines, and form submits are instantaneous. The clinic desk has no patience for entrance animations on every section.

Accessibility

WCAG 2.1 AA:

  • All text ≥ 4.5:1 on --paper; --ink-2 is 9.7:1, safe.
  • Focus visible 2px accent outline, never removed.
  • All interactive elements reachable by Tab, in reading order.
  • Tables have <th scope="col"> headers.
  • Status uses text + swatch, never color alone.
  • Form errors programmatically associated via aria-describedby.

Forbidden

  • Inter, system-ui as a final answer, or any other "AI dashboard" face.
  • Gray text on colored surfaces.
  • Drop shadows.
  • Border-left or border-right > 1px on cards, callouts, or list items.
  • Rounded corners > 2px.
  • Hero-metric template (big number + small label + 3 supporting stats + accent).
  • Nested cards.
  • Gradient text.
  • Eyebrow labels above every section heading.
  • Animation on hover of every list item.

Versión: 1.0 Estado: Borrador - Fase de Inicio (RUP) Producto: VetSys - Sistema Integrado de Gestión Veterinaria Metodología: Proceso Unificado de Rational (RUP)

1. Propósito del Documento

Establecer el alcance, los objetivos de negocio y la justificación del proyecto VetSys, definiendo el valor que el sistema aportará a la clínica veterinaria objetivo. Este documento sirve como acuerdo entre los stakeholders y el equipo de desarrollo, y como referencia para la toma de decisiones durante las fases de RUP.

2. Contexto del Negocio

La clínica veterinaria opera actualmente con procesos manuales y dispersos:

  • Agendas escritas en libretas o planillas sin validación de disponibilidad.
  • Historias clínicas de mascotas archivadas en carpetas físicas, sin respaldo digital.
  • Control de inventario de medicamentos mediante conteo manual.
  • Facturación emitida al final del día con cálculos y consolidaciones manuales.
  • Pérdida recurrente de información por daño de soportes, rotación de personal o extravío.

Estas prácticas generan errores operativos, demoras en la atención, pérdida de ingresos por cobro incorrecto y deterioro en la percepción del cliente.

3. Problemas a Resolver

Código Problema Impacto actual
P-01 Sobrecitación y choques de horarios en agenda manual Cliente espera o se retira sin atención
P-02 Historias clínicas dispersas o extraviadas Diagnósticos sin contexto histórico
P-03 Errores de cálculo en facturación manual Pérdida de ingresos, quejas del cliente
P-04 Stock de medicamentos sin control en tiempo real Venta de productos sin existencia, desabastecimiento
P-05 Ausencia de trazabilidad de prescripciones Imposible auditar qué se suministró y a qué mascota
P-06 Falta de recordatorios automáticos Alta tasa de inasistencia a citas programadas
P-07 Reportes operativos inexistentes o tardíos Decisiones administrativas sin datos

4. Oportunidad de Negocio

La digitalización integral de la operación clínica permite:

  1. Reducir tiempo administrativo destinado a tareas repetitivas.
  2. Aumentar la precisión en el cobro de servicios y productos.
  3. Mejorar la fidelización del cliente mediante atención más ágil y profesional.
  4. Generar indicadores operativos (citas atendidas, productos despachados, ingresos por servicio) para la toma de decisiones.

5. Objetivos del Sistema

5.1 Objetivo General

Desarrollar e implantar un sistema de información que automatice las operaciones críticas de la clínica veterinaria (pacientes, citas, consultas, inventario y facturación), mejorando la eficiencia operativa y la calidad de atención al cliente.

5.2 Objetivos Específicos

  • OG-01 - Eliminar los choques de horario mediante un calendario digital con validación de disponibilidad.
  • OG-02 - Centralizar el historial clínico de cada mascota asociado a su dueño, con respaldo digital.
  • OG-03 - Reducir a cero los errores aritméticos en facturación mediante cálculo automático.
  • OG-04 - Mantener actualizado el stock de medicamentos tras cada prescripción en consulta.
  • OG-05 - Disminuir la inasistencia mediante recordatorios automáticos por correo electrónico.
  • OG-06 - Producir reportes operativos en tiempo real (diarios, semanales, mensuales).

3. Reglas de Diseño Transversal

  • Roles visibles en navegación superior: el avatar y nombre del usuario debe mostrar el rol activo (Recepción / Veterinario / Administrador).
  • Acciones sensibles bloqueadas por rol: un recepcionista no debe ver botones del módulo Consulta ni Inventario.
  • Mensajería de error consistente: formato Icono + Título + Acción sugerida.
  • Confirmaciones destructivas: Cancelar cita, eliminar registro, etc., requieren modal de confirmación.
  • Estados vacíos: cada listado debe mostrar mensaje amigable si no hay datos, nunca tabla vacía silenciosa.

3. Multiplicidad (cardinalidad) explícita

Relación Multiplicidad Lectura
Dueño → Mascota 1 a 1..* Un dueño posee una o varias mascotas
Mascota → Historial Clínico 1 a 1 Cada mascota tiene exactamente un historial clínico
Historial → Entrada 1 a 1..* Un historial registra una o varias entradas a lo largo del tiempo
Mascota → Cita 1 a 0..* Una mascota puede tener ninguna o varias citas
Cita → Consulta 1 a 0..1 Una cita origina a lo sumo una consulta
Consulta → Prescripción 1 a 1..* Una consulta puede tener una o varias prescripciones
Consulta → Servicio 1 a 1..* Una consulta puede incluir uno o varios servicios
Prescripción → Producto *..1 a 1 Una prescripción referencia exactamente un producto
Consulta → Servicio (vía ConsultaServicio) *..1 a 1 Asociación N:M controlada con atributos
Consulta → Factura 1 a 0..1 Una consulta origina a lo sumo una factura
Factura → ItemFactura 1 a 1..* Una factura contiene uno o varios ítems
Usuario (rol Vet) → Cita 1 a 0..* Un veterinario atiende varias citas
Usuario (rol Vet) → Consulta 1 a 0..* Un veterinario firma varias consultas

4. Notas de Diseño

  • Usuario generaliza los tres roles (Administrador, Veterinario, Recepción). El atributo rol decide permisos vía RBAC.
  • HistorialClinico se modela como entidad independiente 1:1 con Mascota para permitir metadata (fecha apertura, notas generales, estado activo/cerrado). Las entradas individuales se almacenan en EntradaHistorial.
  • ConsultaServicio materializa la relación N:M entre Consulta y Servicio, permitiendo guardar el precio histórico por si el servicio cambia de tarifa.
  • ItemFactura cubre tanto servicios como productos consumidos; el campo tipo discrimina (SERVICIO | PRODUCTO).
  • Las recetas/prescripciones se almacenan explícitamente (no se infieren de ItemFactura) porque requieren datos clínicos (dosis, frecuencia, duración) que no son propios de una factura.

3. Caso de Uso Crítico: UC-06 Registrar Consulta Médica

Este es el caso más complejo por su interacción con prescripción, inventario, facturación y archivos. Se documenta con nivel de detalle expandido.

3.1 Metadatos

Campo Valor
ID UC-06
Nombre Registrar Consulta Médica
Actor primario Veterinario
Precondiciones Veterinario autenticado; cita seleccionada en estado CONFIRMADA o EN_CURSO
Postcondiciones Consulta registrada con diagnóstico, prescripciones (si aplica) y factura emitida
Frecuencia estimada 8-15 veces al día
Criticidad Alta

3.2 Flujo Principal (Éxito)

Paso Actor Acción
1 Veterinario Selecciona la cita del día desde el panel de citas programadas
2 Sistema Muestra datos de la cita + mascota + historial clínico resumido
3 Veterinario Abre el formulario "Nueva Consulta"
4 Sistema Despliega campos: síntomas, diagnóstico, tratamiento, observaciones
5 Veterinario Ingresa síntomas observados
6 Veterinario Ingresa diagnóstico
7 Veterinario Selecciona servicios realizados (ej. consulta general + aplicación de vacuna)
8 Sistema Registra cada servicio con su precio vigente y lo acumula en pre-factura
9 Veterinario Opcional: agrega prescripción de uno o varios productos desde inventario
10 Sistema Para cada producto: valida stock, descuenta cantidad y suma al acumulado de pre-factura
11 Veterinario Opcional: adjunta archivos (imágenes, resultados de laboratorio)
12 Sistema Almacena archivos en volumen y registra metadatos
13 Veterinario Pulsa "Finalizar Consulta"
14 Sistema Abre transacción SQL, persiste consulta + prescripciones + factura + items
15 Sistema Genera número de factura correlativo, muestra resumen al veterinario
16 Sistema Cambia el estado de la cita a ATENDIDA y de la factura a EMITIDA
17 Sistema Registra entradas en el historial clínico de la mascota

3.5 Flujos Alternativos

A1 - Stock insuficiente (paso 10): - 10a. Sistema detecta que el stock del producto es menor a la cantidad solicitada. - 10b. Muestra alerta indicando: producto, stock disponible, cantidad solicitada. - 10c. Veterinario decide: (i) ajustar cantidad al stock disponible, (ii) seleccionar otro producto, (iii) posponer prescripción. - 10d. Si acepta (i), continúa con la cantidad ajustada.

A2 - Cancelar consulta en curso (paso 13): - 13a. Veterinario pulsa "Cancelar". - 13b. Sistema requiere confirmación. - 13c. Si confirma: cita queda en estado NO_ATENDIDA, no se genera factura, se libera inventario (rollback), se registra motivo en bitácora.

A3 - Error al adjuntar archivo (paso 11): - 11a. Sistema falla al guardar el archivo (disco lleno, permisos). - 11b. Muestra mensaje de error específico del catálogo de excepciones. - 11c. Veterinario puede reintentar o continuar sin el archivo (consulta no se bloquea).

3.6 Reglas de Negocio

Código Regla
RN-01 Una cita solo puede generar una consulta
RN-02 Una consulta puede registrar N prescripciones, pero cada prescripción referencia exactamente un producto
RN-03 El descuento de inventario debe ser atómico (transacción); si falla algo, se hace rollback completo
RN-04 La factura no se puede eliminar una vez emitida; solo anular (requiere rol Administrador)
RN-05 El historial clínico de la mascota se actualiza de forma automática al cerrar la consulta
RN-06 El número de factura es correlativo y único por clínica, sin reinicios
RN-07 La sesión del veterinario debe estar activa para acceder al flujo

UC-09 Generar Factura (automático al cerrar consulta)

Ver prototype/consulta-flow.ts para la lógica transaccional. La factura se crea dentro del BEGIN/COMMIT al finalizar consulta.

Elementos incluidos automáticamente

  • Servicios: cada consulta_servicio con su precio_cobrado congelado.
  • Productos: cada prescripcion con precio_unitario_cobrado congelado.
  • Subtotal: suma de servicios + productos.
  • Impuestos: subtotal * TAX_RATE (configurable por clínica).
  • Total: subtotal + impuestos.
  • Número: F-{año}-{secuencia} desde factura_numero_seq.
  • Estado inicial: EMITIDA.

Acciones posteriores posibles

  • Pagar factura (rol Recepción) → estado PAGADA.
  • Anular factura (rol Administrador) → estado ANULADA, requiere motivo en bitácora.

  FROM 'duenos.csv' WITH (FORMAT csv, HEADER true)"

echo "Cargando mascotas..."
psql -U $USER -d $DB <<'SQL'
CREATE TEMP TABLE tmp_mascotas (
  dueno_dni varchar(20),
  nombre varchar(120),
  especie varchar(60),
  raza varchar(120),
  fecha_nacimiento date,
  sexo varchar(20),
  peso_kg numeric,
  microchip varchar(60)
);

\copy tmp_mascotas FROM 'mascotas.csv' WITH (FORMAT csv, HEADER true)

INSERT INTO vetsys.mascota
  (dueno_id, nombre, especie, raza, fecha_nacimiento, sexo, peso_kg, microchip)
SELECT d.id, t.nombre, t.especie, t.raza, t.fecha_nacimiento, t.sexo::sexo_mascota, t.peso_kg, t.microchip
FROM tmp_mascotas t
JOIN vetsys.dueno d ON d.dni = t.dueno_dni;

INSERT INTO vetsys.historial_clinico (mascota_id, fecha_apertura, notas_generales)
SELECT m.id, CURRENT_DATE, 'Historia importada de planilla'
FROM vetsys.mascota m
WHERE NOT EXISTS (SELECT 1 FROM vetsys.historial_clinico h WHERE h.mascota_id = m.id);

DROP TABLE tmp_mascotas;

Fase: Transición Audiencia: Recepción / Caja / Veterinario (usuarios del sistema)

1. Inicio de Sesión

  1. Abrir navegador en https://vetsys.clinica.com.
  2. Ingresar usuario y contraseña.
  3. Pulsa "Ingresar".
  4. El sistema recuerda la sesión por 8 horas.

Recuperación de contraseña: contactar al administrador. El admin la resetea y le entrega una temporal.

2. Recepción - Operaciones Diarias

2.1 Registrar dueño nuevo

  1. Menú → Pacientes → "+ Nuevo dueño".
  2. Completar DNI, nombre, apellido, teléfono, email (opcional), dirección (opcional).
  3. Confirmar.

2.2 Registrar mascota

  1. Desde la ficha del dueño → "+ Nueva mascota".
  2. Completar nombre, especie, raza, fecha nacimiento, sexo, peso.
  3. (Opcional) Microchip si tiene.
  4. Confirmar. El sistema crea automáticamente el historial clínico.

2.3 Agendar cita

  1. Menú → Agenda → "+ Nueva cita".
  2. Buscar mascota por DNI del dueño o nombre de mascota.
  3. Seleccionar fecha, hora y veterinario.
  4. Tipo: Consulta / Vacuna / Cirugía / Control / Otro.
  5. Motivo (mínimo 5 caracteres).
  6. Confirmar.

Códigos de error frecuentes:

  • EX-009 - Slot ocupado: cambiar hora o veterinario.
  • EX-007 - DNI duplicado: verificar si el dueño ya existe.

2.4 Reprogramar cita

  1. Abrir cita desde el calendario.
  2. Pulsa "Reprogramar".
  3. Elegir nueva fecha y hora.
  4. Ingresar motivo de reprogramación.
  5. Confirmar.

2.5 Cancelar cita

  1. Abrir cita.
  2. Pulsa "Cancelar".
  3. Confirmar e ingresar motivo.
  4. Las citas ATENDIDAS no se pueden cancelar (EX-010).

3. Veterinario - Atención Clínica

3.1 Abrir consulta

  1. Menú → Citas de hoy.
  2. Seleccionar cita.
  3. Pulsa "Iniciar consulta".
  4. La cita pasa a estado EN_CURSO.

3.2 Registrar síntomas y diagnóstico

  • Completar campos obligatorios: síntomas y diagnóstico.
  • Tratamiento y observaciones son opcionales pero recomendados.

3.3 Agregar servicios

  1. "+ Servicio".
  2. Buscar por nombre o código.
  3. Seleccionar y confirmar.
  4. Repetir si hay más servicios.

3.4 Prescribir medicamento

  1. "+ Medicamento".
  2. Buscar producto por nombre o SKU.
  3. Indicar cantidad, dosis, frecuencia, duración.
  4. Confirmar.

Si el sistema muestra EX-011: stock insuficiente. Ajustar cantidad o elegir otro producto.

3.5 Adjuntar archivos

  1. "+ Archivo".
  2. Arrastrar imagen o PDF (máx 10 MB, formatos: PNG, JPEG, WEBP, PDF).
  3. Confirmar.

3.6 Finalizar consulta

  1. Pulsa "Finalizar Consulta".
  2. El sistema: - Genera factura con número correlativo. - Descuenta stock definitivamente. - Actualiza historial clínico. - Cambia cita a ATENDIDA.

4. Caja - Cobro

4.1 Ver factura del día

  1. Menú → Facturación.
  2. Lista de facturas del día (por defecto).
  3. Seleccionar factura.

4.2 Cobrar

  1. Abrir factura.
  2. Verificar desglose: servicios + productos + impuestos.
  3. Pulsa "Cobrar".
  4. Estado cambia a PAGADA.

Opcional: exportar PDF o imprimir.

4.3 Anular factura (solo Administrador)

  1. Abrir factura.
  2. Pulsa "Anular".
  3. Ingresar motivo.
  4. Confirmar. Estado → ANULADA.

Importante: factura anulada no se elimina; queda en bitácora.

} } async function fetchNextFacturaNumber(client: PoolClient): Promise<string> { const { rows } = await client.query<{ nextval: string }>( "SELECT nextval('factura_numero_seq') AS nextval", ); const seq = rows[0].nextval; const year = new Date().getFullYear(); return `F-${year}-${seq.padStart(8, "0")}`; } // --------------------------------------------------------------------------- // Núcleo del prototipo: registrarConsulta() // --------------------------------------------------------------------------- export interface ConsultaResult { consultaId: number; facturaId: number; facturaNumero: string; total: number; } export async function registrarConsulta( input: ConsultaInput, ): Promise<ConsultaResult> { return withTransaction(async (client) => { // 1) Validar cita y bloquear fila const citaRes = await client.query<{ id: number; mascota_id: number; dueno_id: number; estado: string; }>( `SELECT c.id, c.mascota_id, m.dueno_id, c.estado FROM cita c JOIN mascota m ON m.id = c.mascota_id WHERE c.id = $1 FOR UPDATE`, [input.citaId], ); if (citaRes.rowCount === 0) throw new Error("EX-009 Cita no encontrada"); const cita = citaRes.rows[0]; if (cita.estado !== "PROGRAMADA" && cita.estado !== "CONFIRMADA") { throw new Error( `EX-010 No se puede atender cita en estado ${cita.estado}`, ); } // 2) Insertar consulta (cabecera clínica) if (!input.sintomas || !input.diagnostico) { throw new Error("EX-013 Síntomas y diagnóstico son obligatorios"); } const consultaRes = await client.query<{ id: number }>( `INSERT INTO consulta (cita_id, mascota_id, veterinario_id, sintomas, diagnostico, tratamiento, observaciones) VALUES ($1, $2, $3, $4, $5, $6, $7) RETURNING id`, [ input.citaId, cita.mascota_id, input.veterinarioId, input.sintomas, input.diagnostico, input.tratamiento ?? null, input.observaciones ?? null, ], ); const consultaId = consultaRes.rows[0].id; // 3) Registrar servicios (precio congelado) for (const s of input.servicios) { const svcRes = await client.query<{ nombre: string; precio: string; activo: boolean; }>( `SELECT nombre, precio, activo FROM servicio WHERE id = $1`, [s.servicioId], ); if (svcRes.rowCount === 0) throw new Error(`EX-019 Servicio ${s.servicioId} inexistente`); const svc = svcRes.rows[0]; if (!svc.activo) throw new Error(`EX-012 Servicio ${svc.nombre} inactivo`); await client.query( `INSERT INTO consulta_servicio (consulta_id, servicio_id, cantidad, precio_cobrado) VALUES ($1, $2, $3, $4)`, [consultaId, s.servicioId, s.cantidad, svc.precio], ); } // 4) Procesar prescripciones (descuento atómico de stock) for (const p of input.prescripciones) { // 4a) Bloquear fila del producto para evitar race conditions const prodRes = await client.query<{ id: number; nombre: string; stock_actual: number; activo: boolean; precio_venta: string; }>( `SELECT id, nombre, stock_actual, activo, precio_venta FROM producto WHERE id = $1 FOR UPDATE`, [p.productoId], ); if (prodRes.rowCount === 0) { throw new Error(`EX-019 Producto ${p.productoId} inexistente`); } const prod = prodRes.rows[0]; if (!prod.activo) { throw new Error(`EX-012 Producto ${prod.nombre} inactivo`); } if (prod.stock_actual < p.cantidad) { throw new Error( `EX-011 Stock insuficiente para ${prod.nombre}. Disponible: ${prod.stock_actual}, solicitado: ${p.cantidad}`, ); } // 4b) UPDATE del stock await client.query( `UPDATE producto SET stock_actual = stock_actual - $1, updated_at = NOW() WHERE id = $2`, [p.cantidad, p.productoId], ); // 4c) Insertar prescripción con precio congelado await client.query( `INSERT INTO prescripcion (consulta_id, producto_id, cantidad, dosis, frecuencia, duracion, precio_unitario_cobrado) VALUES ($1, $2, $3, $4, $5, $6, $7)`, [ consultaId, p.productoId, p.cantidad, p.dosis ?? null, p.frecuencia ?? null, p.duracion ?? null, prod.precio_venta, ], ); } // 5) Calcular subtotal desde consulta_servicio + prescripcion const totalesRes = await client.query<{ subtotal: string }>( `SELECT COALESCE(( SELECT SUM(cs.cantidad * cs.precio_cobrado) FROM consulta_servicio cs WHERE cs.consulta_id = $1 ), 0) + COALESCE(( SELECT SUM(p.cantidad * p.precio_unitario_cobrado) FROM prescripcion p WHERE p.consulta_id = $1 ), 0) AS subtotal`, [consultaId], ); const subtotal = Number(totalesRes.rows[0].subtotal); const impuestos = Number((subtotal * TAX_RATE).toFixed(2)); const total = Number((subtotal + impuestos).toFixed(2)); // 6) Crear factura correlativa const numero = await fetchNextFacturaNumber(client); const facturaRes = await client.query<{ id: number }>( `INSERT INTO factura (numero, consulta_id, dueno_id, subtotal, impuestos, total, estado) VALUES ($1, $2, $3, $4, $5, $6, 'EMITIDA') RETURNING id`, [numero, consultaId, cita.dueno_id, subtotal, impuestos, total], ); const facturaId = facturaRes.rows[0].id; // 7) Items de factura (servicios) await client.query( `INSERT INTO item_factura (factura_id, tipo, ref_id, descripcion, cantidad, precio_unitario, subtotal) SELECT $1, 'SERVICIO', s.id, s.nombre, cs.cantidad, cs.precio_cobrado, cs.cantidad * cs.precio_cobrado FROM consulta_servicio cs JOIN servicio s ON s.id = cs.servicio_id WHERE cs.consulta_id = $2`, [facturaId, consultaId], ); // 8) Items de factura (productos) await client.query( `INSERT INTO item_factura (factura_id, tipo, ref_id, descripcion, cantidad, precio_unitario, subtotal) SELECT $1, 'PRODUCTO', p.id, pr.nombre, p.cantidad, p.precio_unitario_cobrado, p.cantidad * p.precio_unitario_cobrado FROM prescripcion p JOIN producto pr ON pr.id = p.producto_id WHERE p.consulta_id = $2`, [facturaId, consultaId], ); // 9) Actualizar estado de cita await client.query( `UPDATE cita SET estado = 'ATENDIDA', updated_at = NOW() WHERE id = $1`, [input.citaId], ); // 10) Entrada automática en historial clínico await client.query( `INSERT INTO entrada_historial (historial_id, fecha, tipo, descripcion, autor_id) SELECT hc.id, NOW(), 'CONSULTA', $2 || ' - ' || $3, $4 FROM historial_clinico hc WHERE hc.mascota_id = $1`, [ cita.mascota_id, input.sintomas.slice(0, 100), input.diagnostico.slice(0, 100), input.veterinarioId, ], ); return { consultaId, facturaId, facturaNumero: numero, total, }; }); } // --------------------------------------------------------------------------- // Smoke test (no se ejecuta en producción) // --------------------------------------------------------------------------- if (import.meta.main) { const demo = await registrarConsulta({ citaId: 1, veterinarioId: 1, sintomas: "Cojera en pata trasera derecha", diagnostico: "Esguince leve", tratamiento: "Reposo + antiinflamatorio", servicios: [{ servicioId: 1, cantidad: 1 }], prescripciones: [{ productoId: 1, cantidad: 2, dosis: "1 comp", frecuencia: "12h", duracion: "5 dias" }], });
